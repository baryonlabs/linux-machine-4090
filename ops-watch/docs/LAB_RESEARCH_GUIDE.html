본 서버(martin-B650M-K)는 연구원들의 안전한 연구를 위해 Docker 컨테이너 격리 방식으로 운영됩니다.
호스트 OS에 패키지를 직접 설치하지 않고, 연구원 각자에게 할당된 독립된 JupyterLab (PyTorch 24.04-py3) 컨테이너 안에서 작업을 수행합니다.

🚀 1. 빠른 시작 & 온보딩 가이드
3단계 완성

Step 1 Headscale VPN 연결

연구실 서버는 보안을 위해 외부 공인 IP가 닫혀 있으며, Headscale WireGuard 오버레이 네트워크를 통해 암호화 터널로만 접속 가능합니다. 

# 로컬 PC에서 Tailscale 클라이언트 설치 후 실행
tailscale up --login-server http://100.64.0.1:8080 --authkey <발급받은_PRE_AUTH_KEY>

✔ 연결 성공 시 연구실 사설 IP 대역(100.64.0.0/10)에 자동으로 등록됩니다.

Step 2 개인 전용 JupyterLab 접속

연구원마다 고유한 포트(8888, 8889, 8890, 8891...)와 전용 보안 토큰이 부여된 독립 컨테이너가 배정됩니다. 

# 브라우저 주소창에 본인 전용 URL 입력:
http://100.64.0.2:<할당된_포트>/?token=<할당된_토큰>

✔ 접속 즉시 8TB 대용량 스토리지(/mnt/data/users/<user>)가 루트(/workspace)로 열려 용량 걱정 없이 즉시 실험을 시작할 수 있습니다.

Step 3 터미널 SSH 접속 (선택 사항)

CLI 스크립트 실행이나 tmux 작업이 필요한 경우, 비표준 포트 2322로 SSH 접속합니다: 

ssh -p 2322 <username>@100.64.0.2

💾 2. 기본 시작 폴더 & 스토리지 분리 아키텍처
8TB 대용량 스토리지 기본 마운트

JupyterLab의 기본 시작 작업 디렉토리(/workspace)는 8TB 대용량 스토리지 내의 독립 작업 폴더(/mnt/data/users/<user>/jupyter_home)로 설정되어 있습니다.
따라서 새로 생성하는 노트북 및 프로젝트 파일이 깔끔하게 격리되어 관리되며, 8TB HDD에 저장되므로 시스템 NVMe 루트 디스크가 꽉 차는 사고를 근본적으로 방지합니다.
상위 데이터 폴더(data_root/) 및 개인 홈 디렉토리(home/)도 탐색기 내에서 바로 접근할 수 있습니다.

JupyterLab 탐색기 경로 호스트 실제 경로 권장 용도 용량 및 특성
/workspace (기본 시작 폴더) /mnt/data/users/<username>/jupyter_home 개인 연구 노트북, 실험 코드, 프로젝트 작업공간 8TB 대용량 스토리지 (전용 독립 홈 폴더)
/workspace/data_root /mnt/data/users/<username> 대용량 비디오 데이터셋, HuggingFace 캐시, 8B 모델 가중치 8TB 대용량 스토리지 (공유 및 대용량 I/O 저장소)
/workspace/home /home/<username> 개인 bash 설정, SSH 키, git repos, 가벼운 설정 파일 루트 914GB NVMe (대용량 파일 저장 금지, 개인 설정용)
💡 HuggingFace 캐시 디렉토리 설정:
노트북 시작 시 아래 환경 변수를 지정하여 HuggingFace와 PyTorch 캐시가 대용량 볼륨의 캐시 폴더로 지정되도록 권장합니다:

⚡ 3. 단일 GPU 자원 점유 에티켓 & 좀비 커널 방지
24GB VRAM 독점 방지
🚨 가장 빈번한 장애 원인: "브라우저 창만 닫고 커널 유지"
Jupyter Notebook 웹 브라우저 탭을 닫아도 PyTorch가 점유한 24GB VRAM은 절대 반납되지 않습니다!
실험이 끝난 후 커널을 켜두면 다른 연구원이 즉시 CUDA out of memory 에러를 겪게 됩니다.

❌ 잘못된 종료 방식

  • 브라우저 탭/창만 닫기 (VRAM 그대로 점유)
  • 노트북에서 예외(Exception) 발생 후 방치
  • OOM 에러 발생 후 셀 재실행하지 않고 방치

✔ 올바른 자원 반납 절차

  1. 상단 메뉴: Kernel ➔ Shut Down All Kernels 클릭
  2. 또는 좌측 사이드바: 'Running Terminals and Kernels' (정지 아이콘) 클릭 후 Shut Down
  3. Ops-Watch 대시보드(포트 23450)에서 본인 컨테이너의 GPU 점유가 0MB인지 확인

🤖 Ops-Watch v2의 자동 좀비 커널 감지 (ZombieKernelDetector)

VRAM을 4GB 이상 점유하면서 GPU/CPU 연산률이 0%인 상태로 30분 이상 방치되는 경우, Ops-Watch 온톨로지 엔진이 이를 zombie_jupyter_kernel로 판정하고 알림 티켓을 발행하여 관리자가 원격으로 커널 프로세스를 회수할 수 있습니다.

🧠 4. 8B LLM 파인튜닝 연구법 (RTX 4090 24GB 맞춤)
LoRA • QLoRA • FlashAttention-2 • ZeRO-2

8B 모델(LLaMA-3-8B, Qwen-2.5-7B, Mistral-7B)은 기본 FP16 가중치만 16GB에 달하며, AdamW 옵티마이저와 Gradient를 더하면 40GB 이상의 VRAM이 필요합니다.
단일 24GB RTX 4090에서 OOM 없이 안정적으로 학습하기 위한 3대 최적화 기법을 반드시 적용하세요.

✨ 최적화 1: 4-bit QLoRA (BitsAndBytes NF4)

모델 가중치를 4비트로 양자화하여 VRAM 점유를 약 5.5GB로 압축하고, 학습 가능한 LoRA 어댑터(q_proj, v_proj 등)만 FP16으로 훈련합니다. 

import torch
from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig
from peft import LoraConfig, get_peft_model, prepare_model_for_kbit_training

# 1. 4-bit 양자화 설정 (VRAM ~5.5GB 소비)
bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_compute_dtype=torch.bfloat16,
    bnb_4bit_use_double_quant=True
)

model_id = "meta-llama/Meta-Llama-3-8B-Instruct"
tokenizer = AutoTokenizer.from_pretrained(model_id, cache_dir="/workspace/data/cache")

model = AutoModelForCausalLM.from_pretrained(
    model_id,
    quantization_config=bnb_config,
    device_map="auto",
    attn_implementation="flash_attention_2", # FlashAttention-2 필수 적용
    cache_dir="/workspace/data/cache"
)

# 2. Gradient Checkpointing 활성화 (활성화 텐서 메모리 60% 절감)
model = prepare_model_for_kbit_training(model)
model.gradient_checkpointing_enable()

# 3. LoRA 어댑터 설정 (Rank 16, Alpha 32)
lora_config = LoraConfig(
    r=16,
    lora_alpha=32,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj", "gate_proj", "up_proj", "down_proj"],
    lora_dropout=0.05,
    bias="none",
    task_type="CAUSAL_LM"
)

model = get_peft_model(model, lora_config)
model.print_trainable_parameters()
# 결과: Trainable params: 0.1% ~ 0.3% | 총 VRAM 점유: 약 12~14GB 내외로 24GB 대비 안전!

⚡ 최적화 2: DeepSpeed ZeRO-2 CPU-Offload

16비트 LoRA 학습 시 옵티마이저 상태(AdamW 모멘텀/분산)를 호스트의 64GB DDR5 RAM으로 오프로드하여 VRAM을 8GB 이상 확보합니다.

🎬 5. 대용량 비디오 데이터셋 처리 & NVMe 발열 방지
PCIe 4.0 Thermal Throttling Guard

🚨 대용량 비디오 처리 시 겪는 2대 문제

  1. Bus error (core dumped): Docker 기본 공유 메모리(64MB) 한계로 인해 멀티프로세스 DataLoader 크래시 발생.
  2. NVMe SSD 과열 (75°C+ 쓰로틀링): 수만 개의 작은 mp4 파일을 무작위(Random) 개별 디코딩 시 읽기 속도가 1/10로 급락하고 시스템 프리징 유발.

🛡️ Ops-Watch 권장 해결책

  • 우리 Docker 환경은 --ipc=host 및 shm_size: 16gb로 설정되어 공유 메모리 Bus Error가 완벽히 차단되어 있습니다.
  • 비디오 파일은 개별 파일 로딩 대신 WebDataset (.tar 샤드) 포맷으로 묶어서 순차 스트리밍(Sequential Read)하세요.
  • PyTorch num_workers=4~8 권장 (과도한 32개 설정 금지).

💡 안전한 비디오 DataLoader & NVMe 온도 감시 코드

대용량 비디오 학습 루프에 아래와 같이 DataLoader 최적 옵션과 발열 보호 루틴을 적용하세요: 

import torch
from torch.utils.data import DataLoader

# 1. 고속 비디오 I/O를 위한 DataLoader 최적 옵션
train_loader = DataLoader(
    dataset,
    batch_size=4,
    shuffle=True,
    num_workers=4,            # 과도한 worker 수 지양 (4~8 권장)
    pin_memory=True,          # CPU ➔ GPU 텐서 전송 속도 가속
    persistent_workers=True,  # 에포크마다 워커를 재생성하지 않고 유지
    prefetch_factor=2
)

# 2. 비디오 학습 루프 내 NVMe 발열 방지 슬립 체크 (선택 사항)
def get_nvme_temp():
    try:
        with open("/sys/class/hwmon/hwmon1/temp1_input", "r") as f:
            return float(f.read().strip()) / 1000.0
    except Exception:
        return 50.0

for step, batch in enumerate(train_loader):
    # NVMe 온도가 65°C를 초과하면 잠시 0.5초 쿨다운
    if step % 200 == 0:
        temp = get_nvme_temp()
        if temp > 65.0:
            print(f"[NVMe Thermal Guard] 온도가 {temp:.1f}°C로 상승하여 0.5초 쿨다운합니다.")
            import time; time.sleep(0.5)
            
    loss = model(**batch).loss
    loss.backward()
    optimizer.step()
    optimizer.zero_grad()
